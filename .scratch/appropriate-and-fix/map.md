# Appropriate the fork and fix the reviewed bugs

Label: wayfinder:map

## Destination

A repo that is unmistakably **Ding** — its own name, package, identity and docs, carrying no trace of upstream ownership beyond the GPL attribution it is legally obliged to keep — that builds and passes a **green, executable quality gate** both on this machine and in CI, and in which **every finding of the 02-09-2026 code review** has been either fixed or consciously ruled out of scope.

Reminder *features* are not part of this map. The missing functionality that motivated the fork is a separate effort, charted once the state model is trustworthy.

## Notes

**Domain.** Single-module Android app, Kotlin + some legacy Java. GPL-3.0-or-later hard fork of `felixwiemuth/SimpleReminder` at `d34bf2f` (2025-10-20). Source review: `simple-reminder-code-review-02-09-2026.md` at the repo root.

**This map carries execution.** Unlike the wayfinder default, tickets here deliver working, gate-green changes — not just decisions. The user's brief was to *do* the appropriation and *fix* the bugs. The `grilling` tickets are the exception: they resolve a decision, and their implementation is a separate ticket.

**Which skill works which ticket.** The routing is per-ticket, not per-map — do not re-enter `/wayfinder` for the whole map.

- **`Type: grilling`** (09, 16, 18) → **`/wayfinder`**. Genuine fog; the answer does not exist yet. This is what the skill is for.
- **`Type: task`** (everything else) → **`/implement`**. The decision was already made during charting, so these are agent-ready in the sense `/to-tickets` means it. `/implement` drives `/tdd` where there is a seam, then `/code-review`s the diff before committing. Wayfinder's collapse step has already happened for these and running it again adds ceremony, not thinking.
- Some `task` tickets are smaller than `/implement` — ticket 01 is two `git config` commands with nothing to test and no diff worth reviewing. Just do it.

Whichever route, do the bookkeeping by hand afterwards: set `Status: resolved` on the ticket and append one line to *Decisions so far* below. Two lines; not worth a skill.

**Skills every session should consult.** `/grilling` and `/domain-modeling` for any `grilling` ticket; `/tdd` for anything touching reminder state or storage.

**Hard constraints.**
- **GrapheneOS / AOSP compatible, always.** No Google, GMS, Play Services or Firebase dependency may ever enter the graph. The app is Google-free today and has run reliably on GrapheneOS for years — this is a property to *keep*, not to build.
- `minSdk 31`, `targetSdk 36`.
- **No personal email address anywhere** in the repo, in commit metadata, or in published artifacts.
- Never commit red gates.

**Working conventions** (adopted from `../Loquace/CLAUDE.md`, trimmed to a single-module app):
- Plain language, no invented jargon. Name things by what they do.
- A ticket must fit one fresh agent at low context. If it looks bigger, split it first.
- **One long-lived branch: `main`.** Code changes happen in short-lived worktrees on ticket branches, one ticket each, merged back with `--no-ff`. Releases are marked by tags, not by a branch.
- Commit trailer names the model that actually wrote the code: `Co-authored-by: Opus 5 <noreply@anthropic.com>`. A non-Anthropic model uses its own name and vendor no-reply address.

### Settled while charting

These are the answers that fixed the destination. They are not tickets and were decided in conversation on 2026-09-04.

- **Scope** — bounded first milestone. Repo is ours, gate is green, every review finding fixed or ruled out. Features are a later map.
- **Name** — **Ding**. `applicationId` and `namespace` both become `app.ding`, matching the `app.loquace` house style. The GitHub repo and this working directory get renamed too.
- **Hard fork** — upstream is never merged again. Anything interesting gets cherry-picked by hand. This is what buys the freedom to raise `minSdk` and restructure at will.
- **Single trunk** — upstream's git-flow `develop`/`main` split is retired. It cost a second merge per release and bought nothing for a single maintainer publishing via GitHub releases.
- **Distribution** — public GitHub releases, built so F-Droid stays cheap later. Not the Play Store.
- **Bug-fix depth** — both the bounded fixes and the structural ones, but structural work makes its *decisions* here and its code in follow-on tickets. Room migration is out of scope.
- **CI** — GitHub Actions on the existing public GitHub remote. Free and unlimited for public repos, and the hosted runners ship the Android SDK, which avoids the ~200 lines of SDK bootstrap the self-hosted Forgejo runner needs. The workflow file stays portable if this changes.
- **Crash reporting** — ACRA is removed entirely. No replacement decided; see *Not yet specified*.
- **GrapheneOS verification** — a dependency guard in the gate now; instrumented tests on the existing `bench-pixel6-aosp` emulator (API 36, pure AOSP, Pixel 6 profile) as a later decision.

- [No nag before the due time, and Reconcile cleans up after DONE](issues/23-clock-rollback-and-done-cleanup.md) — **a nag is never earlier than the due time plus one interval, and a reconciliation cleans up after a done reminder.** `nextNagTime` counted occurrences from the due time with `Math.floorMod`, which on a negative difference picks the occurrence *before* it: after the clock is set back, a delivered reminder has a due time ahead of the clock, so due 10:00 with now 09:00 and a ten minute interval armed a nag at 09:10 and went on nagging until the clock caught up. It now answers `dueTime + interval` whenever now is before the due time, which is the same rule read from either side, and is tested an hour and a millisecond before the due time, at it, a millisecond after it, and on exact interval boundaries. Separately, the runner persists before it runs effects, so a process that dies between the write that marks a reminder done and its cancels — or a cancel that fails — left a done reminder with a nag alarm or a notification still there and nothing that would ever repair it; **Reconcile over `DONE` now emits `CancelAlarm` and `CancelNotification`** instead of nothing. The code and the transition table were wrong, not invariant 3, which already said a done reminder has an empty slot and no notification after a reconciliation; both cancels are idempotent so the cost per start is nil. Four new tests, three in the transition suite and one runner test that replays the restart over a fake executor that does nothing, plus test 11 of the model document which had pinned the old behaviour. Reliability findings 6 and 7 of the 2026-09-05 global review. Retention for done reminders — the thing that makes the new cancels grow with the store — is still the open item it was.

- [Keep reminder ids unique in the store and never reused after a quarantine](issues/21-reminder-ids-unique-and-never-reused.md) — **an id is never handed out twice within an install.** Ticket 13's set-aside emptied the id counter along with the reminder list, so the next Add started again from 0 while the notifications, alarms and pending intents of the reminders that had been in the store were all still live in the OS under those very ids: swiping the old notification away sent a mark-done for the *new* reminder, which was cancelled and never fired. `PREF_STATE_NEXTID` is now durable on its own and the set-aside leaves it alone, written in the same rollback-protected commit. A counter that cannot be used is rebuilt rather than reset, by `nextIdAfterQuarantine` in `StoredReminderDecoding.kt` — pure and android-free — as the larger of the stored counter and 2 plus the largest even in-range id an `"id":<number>` occurrence in the quarantined raw text names, rounded up to an even number; the scan is best effort by construction and errs upwards on purpose, since a false match only skips an id that was never used while a missed one hands it out twice. The read and the set-aside share that one function. **Every quarantine now cancels all of the app's notifications**, after the commit and not before, because nothing else would ever take them off the screen; an alarm that arrives for one afterwards takes ticket 10's missing-reminder cleanup path. Separately, **two stored reminders sharing an id are `Unreadable(DUPLICATE_ID, raw)`**: uniqueness is a property of the list, so `Reminder`'s own `require` cannot see it, and the pair shares one alarm slot, one notification and one request code, so the store is set aside whole rather than half-repaired by picking a winner. 16 new JVM tests across the three suites, including the runner test ticket 23's review asked for — a future `SCHEDULED` and a `DONE` reminder sharing an id are quarantined before any effect runs, so `reconcileAll` never emits a `SetAlarm` that a `CancelAlarm` then undoes — and two existing tests that pinned the counter reset were rewritten. Reliability findings 1 and 5 of the 2026-09-05 global review. The `cancelAll` line has no JVM seam and is covered by inspection. Two review findings then took the same rule one step further: **recovering a counter may only ever move it up** — a readable but empty reminder list used to recompute an unusable counter down to 0, which is exactly the reset this ticket closed, reached through the other door — so the stored counter and the largest id anything still records are both read as evidence and the larger wins, with a number that is merely odd rounded up rather than thrown away; and **`MAX_REMINDER_ID + 2` is a counter with no id left rather than damage**, since that is what the store writes by itself after the last allocation, so it survives every read, rebuild and write, and an Add against it answers `Refused(IdSpaceExhausted)` — the dialogs show the existing "could not save" message — instead of lowering the counter or throwing out of `Reminder`'s own require. A third finding closed the last way down: a counter *above* that mark — `EXHAUSTED_ID_COUNTER + 2`, or `Int.MAX_VALUE` — was still discarded as a number the app could not have written, so over an empty readable list the count started again from 0 and the next Add reused id 0. Any non-negative counter at or above the mark is now clamped down to it, before the parity rounding that on `Int.MAX_VALUE` would otherwise overflow, in the one function the read path and the quarantine rebuild share: however far past the end it was pushed it still says ids were handed out, so the counter never decreases and the Add is refused rather than handed an id already in use, while a negative or non-numeric counter still contributes nothing. Five more JVM tests, the clamp logged with the other counter repairs, and the counter `MAX_REMINDER_ID + 4` moved out of the test list of counters with no usable number in them.
- [Make the email guard cover commit metadata and every fork-authored tree](issues/20-email-guard-covers-commits.md) — G1 grepped the current tree and nothing else, which is how two ticket files published the maintainer's address for two commits and left the blobs in history. `scripts/check-no-personal-email.sh` now runs **four checks and reports all of them**: every tracked file in the working tree; **the staged index**, which is what a commit actually takes and which a partial `git add -p` can leave holding what the file on disk no longer does; **the identity the next commit would carry**, both author and committer, which is the check that would have caught ticket 01 before the first commit and still would, since only the repo-local override keeps this machine's personal global `user.email` out of a commit; and **every commit the fork authored**, the range `HEAD ^d34bf2f ^62ef3e8`, 50 today — author, committer, the whole message including trailers, and the commit's own tree, so an address redacted two commits later is still caught. 0.75 s for the whole history, so it stays first in the gate. Every scan reads blobs as text (`-a`) so a NUL byte cannot hide an address, matches case-insensitively, and applies one strict definition of a no-reply address: local part exactly `noreply`, or domain exactly `users.noreply.github.com`, and not the word appearing somewhere in a deliverable one. An identity git cannot report is a failure rather than a pass, the single exception being a GitHub Actions runner, which configures none and commits nothing, where the check is skipped out loud. Tracing is turned off at the top so an inherited `bash -x` cannot print what the script exists to keep quiet. **A shallow clone or a missing exclusion commit is exit 1, not a pass**, and CI checks out with `fetch-depth: 0`. Upstream's **commits** are excluded by reachability, by the range, never by naming an address. The **historical trees** are the one place that rule is knowingly relaxed, and there it is relaxed by address value: they pass over exactly the set of addresses the two boundary trees hold, read out of those two commits at run time and never written into the script. The reason is that the fork's early commits carry upstream's files unchanged, so a strict tree check reports 21 commits and 39 hits and could never go green — and G1 being first in the gate, no commit could ever be made to fix it. Exempting files by blob id instead was tried and deadlocks the same way, on 22 blobs the fork itself wrote. The 2026-09-05 rewrite removed the maintainer's own address and only that; upstream's author address reaches every clone through upstream's own commits, which stay in this ancestry for good since the v0.9.x tags hang off them, so no rewrite of the fork's commits could unpublish it. The exemption applies to historical trees and nothing else — not the working tree, not the index, not an identity, not a commit message — so a fork commit copying that address into a new file is caught before it lands and only the after-the-fact scan tolerates it. Verified on a throwaway branch, since deleted: a personal author address, a personal address in a `Co-authored-by:` trailer, and a file holding an address that a later commit deletes each exit 1 naming the commit, and so do a personal address in the environment, a personal global address with no local override, no identity at all, a depth-1 clone and a repository missing the exclusion commits. Not covered: tags and built artifacts. Everything stays in the one script, so `scripts/check.sh` and CI cannot drift.
- [Direct Boot: implement it, or stop claiming it](issues/16-direct-boot-decision.md) — **the claim goes, the feature is kept for the store redesign.** The receiver declares `LOCKED_BOOT_COMPLETED` but nothing is direct-boot aware, so Android never delivers it, and the startup sweep reads credential-protected preferences that do not exist before the first unlock; upstream's 0.9.12 changelog nonetheless says reminders are scheduled "before logging in". The going-in recommendation was to remove the claim and drop the feature, on the ground that a reboot while locked is rare. It is not: GrapheneOS reboots the device on its own after a configured number of hours locked, and the maintainer's phone is set up that way, so a reminder due between that reboot and the next unlock fires late, routinely. Pre-unlock delivery is therefore wanted, but it means reminder content in device-protected storage readable without the passphrase plus direct-boot-aware components — a storage split, which belongs with the Room migration under *Out of scope* and is written down in `docs/planned-features.md`. Decided: remove `LOCKED_BOOT_COMPLETED` and the HTC-only `QUICKBOOT_POWERON` from the receiver; correct upstream's changelog sentence in place in both files rather than delete it or open a fork release block; say "once it has been unlocked" in the two "Activate on device startup" summaries; add **first unlock** to the glossary. Implementation is ticket 26, a task on the gate alone — the emulator image has no lock credential and cannot show the difference.
- [Decide how alarm delivery gets tested automatically](issues/18-how-to-test-alarm-delivery.md) — **two layers above the pure one, each on the tool that can see it.** The pure layer is already covered; untested is the Android glue in `ReminderManager.kt` (request codes, due-time extras, notification ids, the receiver) and the platform itself. The glue is tested with Robolectric in G3, as JUnit 4 classes run by the vintage engine beside the Kotest specs; the platform with one instrumented smoke on a Gradle-managed device (API 36, AOSP image, Pixel 6), with `connectedDebugAndroidTest` against `bench-pixel6-aosp` as the fallback if the managed device dies the way the hand-launched one does. The device stage is a second script-and-workflow pair under the same drift rule, run locally before every merge to `main` and in CI on push to `main` plus manual dispatch — not a seventh gate stage. First test: the Robolectric round trip from `addReminder` through the fired pending intent to a notification under the reminder's id. Waking a dead process and Doze are fog; reboot automation and an API 31–32 image are out of scope. Implementation is tickets 27 (Robolectric) and 28 (device); the two permission findings become tickets 29 and 30 on ticket 27's harness. Order of the open tickets: 22, 26, 27, 28, 29, 30, 17, 19.

## Not yet specified

- **Waking a dead process at the due time.** Ticket 28's instrumented smoke proves a real alarm fires into a *live* process; a test cannot survive its own process being killed. The field case is a dead process being woken, and only an adb script can drive it: install, add a reminder, force-stop the app, wait, read the notification list from the shell. One script around the emulator harness once ticket 28 has built it; not in Gradle, so its own small ticket then.
- **Delivery under Doze.** `dumpsys deviceidle force-idle` around the same smoke would show whether `setExactAndAllowWhileIdle` and the inexact fallback actually get through. Cheap once the harness exists; sharpen with the dead-process script above. The review's recommendation of a Doze-capable fallback or a persistent warning while exact-alarm access is absent (ticket 30 leaves it out) is a product decision that belongs with this.
- **What replaces ACRA, if anything.** For an app whose entire value is firing reliably *in the background*, a foreground crash reporter may be the wrong instrument. The real question is how a silent failure-to-fire becomes visible at all. Revisit once the state machine (ticket 09) exists and there is something meaningful to observe.
- **Release signing and publishing.** A keystore has to exist, live somewhere safe, and be reachable from a release process without leaking into the repo. Sharpens once the rename lands and there is a first release worth cutting.
- **Moving storage work off the main thread.** The review's performance finding. Ticket 09 put every mutation behind one runner (lock, read, transition, checked write, effects), so there is now exactly one place to make asynchronous. Whether it needs `goAsync()` in the receiver, a coroutine scope, or nothing at all is still open until ticket 10 shows how long the runner takes on a realistic store.
- **Retention for completed reminders.** Done reminders accumulate forever, which is what makes the full-store rewrite grow without bound. Part cleanup, part product decision — needs the feature map's input.
- **Regenerating screenshots and store metadata** under the new name. Trivial mechanically, but nobody has decided what the app should *look* like yet.
- **Resource shrinking on the shipping APK.** `shrinkResources` is set on the debug build type and not on release, so the APK users install is never resource-shrunk. Upstream turned minification on in debug to stay under the 64K dex limit and resource shrinking appears to have come along for the ride. Either release should shrink too, or debug should stop — but which way is a size-versus-build-time call nobody has made.
- **Translations.** Upstream shipped English and a German title. Unclear whether the fork keeps, drops, or expands that.

## Out of scope

- **Room migration** — the review recommends moving reminders to a transactional row-based store. Correctness ordering says fix the transitions before changing the store, and this is a rewrite rather than a fix. Returns only as its own effort — and when it does, delivery before the first unlock after a reboot (Direct Boot, ticket 16) comes with it: that needs reminder content in device-protected storage, which is the same storage split, not a manifest flag.
- **F-Droid and Play Store submission** — distribution is public GitHub releases. F-Droid is kept cheap but not pursued.
- **Staying mergeable with upstream** — hard fork. No design tax is paid to keep `git merge upstream/develop` viable.
- **Reminder feature work** — the missing functionality that motivated the fork. Templates, recurring reminders, per-reminder notification settings, media attachments, auto-complete, and the rest of upstream's abandoned roadmap. This is the *next* map, deliberately deferred until the state model can be trusted.
- **Automating a reboot and the boot-time Reconcile, and an API 31–32 emulator image** — ruled out by ticket 18. A reboot cannot be driven from inside a test and the fork's own cold-start bugs are pinned at the pure layer; the exact-alarm revocation path exists only on API 31 and 32, no image for them is installed, and ticket 30 tests it under Robolectric instead. Ticket 17's manual look on the emulator is the only check for both.
